# Create Tools and Profiles

XSMP Modeler can be extended with custom tools and profiles. A contribution is a
VS Code extension with a manifest entry, a descriptor and a C++ handler. It becomes
available in `xsmp.project` and applies only to the projects that enable it.

The TAS-MDK profile in `extensions/tas-mdk` is a complete example.

## Choose a Contribution Kind

Use a tool when the behavior is optional and task-oriented:

- export or generate extra files
- add checks for a specific workflow
- scaffold optional folders or configuration files

Use a profile when the behavior represents a project convention or target
platform:

- select one project layout or runtime ecosystem
- add profile-specific generation
- add validation rules that should apply to the whole project

Projects can enable several tools, but at most one profile:

```text
project 'mission-demo'
source 'smdl'
profile 'xsmp-sdk'
tool 'smp'
tool 'adoc'
```

## Package Layout

```text
demo-extension/
  package.json
  demo-tool.xsmptool
  server/demo-tool.wasm
  builtins/
```

The manifest lists one entry per tool or profile:

```json
{
  "name": "demo-extension",
  "publisher": "example",
  "contributes": {
    "xsmp": [
      {
        "descriptor": "./demo-tool.xsmptool",
        "handler": "./server/demo-tool.wasm",
        "apiVersion": "^2.0.0",
        "aliases": ["demo"],
        "deprecatedAliases": ["old-demo-tool"],
        "builtins": ["./builtins"],
        "wizard": { "label": "Demo tool", "defaultSelected": false }
      }
    ]
  }
}
```

Paths are resolved inside the extension. `nativeHandler` and `wasiHandler` can
replace `handler` for one kind of server. `nativeHandler` is a path, or an object
keyed by `<platform>-<arch>`.

`apiVersion` says which version of the contribution API the handler needs. The
current one is 2.0.0. Write `*`, a version such as `2`, `2.x` or `2.0.0`, or one of
these after `^`, `~` or `>=`.

The descriptor declares the identifier that projects use:

```text
/**
 * Demo XSMP tool.
 */
tool 'demo-tool'
```

A profile uses a `.xsmpprofile` file and `profile 'demo-profile'`.

## Write the Handler

A handler is a C++ library that the server loads when it starts, and that it then
calls directly: it runs in the server, on the same documents, as a built-in tool
does. A `.wasm` module runs under the WASI server, on every system. A `.so` or
`.dylib` runs under a native server on Linux or macOS. A native server on Windows
loads no handler: use the WASI server there.

A handler shares the types of the server, so it must be built from the same version
of XSMP. The server refuses one built from another, with a message that says so. A
failure in a handler can stop the server, so a handler must not crash.

```cpp
#include <xsmp/Extension.hpp>

void registerTool(xsmp::Contribution& tool, xsmp::XsmpSharedCoreServices&) {
  tool.label = "Demo tool";
  tool.description = "Generates a report for each catalogue.";
  // Add generators, validations and scaffolding here.
}
XSMP_EXTENSION(registerTool)
```

```cmake
xsmp_add_extension(demo-tool SOURCES src/main.cpp)
```

A WASI server exports only what the handlers built with it use, so a handler built
elsewhere that needs something else is refused, with the names that are missing.
Add yours to the build of the server, as `extensions/tas-mdk` does.

## Add a Generator

A generator receives a document's root and the output folder of the project:

```cpp
tool.generators.push_back(
    [](const cursiv::AstNode& node, const std::filesystem::path& output) {
      if (const auto* catalogue = cursiv::ast_cast<xsmp::Catalogue>(&node))
        xsmp::writeFileIfChanged(
            output / "demo-gen" / (std::string(catalogue->name) + ".txt"),
            "Generated by the demo tool\n");
    });
tool.generatedFolders = {"demo-gen"};
```

`generatedFolders` names the folders under the output that generation alone writes
to. Generation writes only the files that change, so an unchanged file keeps its
time. Once all of it has succeeded, it removes from these folders each file that no
generator wrote, and the folders left empty. Links in these folders are removed
before generation, and nothing outside them is touched. A file that cannot be
removed makes the generation fail.

A file that the user completes afterwards goes through `xsmp::writeFileIfMissing`:
it is written only where it is missing, and it cannot be in a generated folder.

`trackedFolders` names the folders where generated files sit beside the user's own:

```cpp
tool.trackedFolders = {
    {.generator = "report", .output = "reports", .folder = "reports"}};
```

Generation lists the files it writes there in `.xsmp/generated-files.json`, under
the names of the generator and of the output. Once it has succeeded, it removes the
listed files that it no longer writes, and leaves every other file alone. Other XSMP
tools read the same list, so keep these names stable.

Two generators that write the same generated file make the generation fail.

## Add Validation

A validation registers its checks under the category it receives, with one check per
type of node. A document runs the category of each profile and tool its project
enables, so a check costs nothing elsewhere:

```cpp
tool.validations.push_back(
    [](xsmp::XsmpSharedCoreServices& shared,
       const cursiv::ValidationCategory& category) {
      auto& language = const_cast<cursiv::CoreServices&>(
          shared.serviceRegistry->getServices({}, "xsmpcat"));
      language.validationRegistry->registerCheck(
          {&cursiv::ast_type_tag<xsmp::Catalogue>, false,
           [](const cursiv::AstNode& node, cursiv::ValidationAcceptor& accept,
              const cursiv::CancellationToken&) {
             accept.warning(node, "Demo check.").keyword("catalogue");
           }},
          &category);
    });
```

## Add Wizard Scaffolding

`label`, `description` and `defaultSelected` describe the contribution in the
project wizard. `wizardPrompts` adds questions of type `string`, `boolean` or
`choice`. `scaffolder` writes the first files of a new project:

```cpp
tool.wizardPrompts = {xsmp::JsonObject{{"id", "moduleName"},
                                       {"type", "string"},
                                       {"label", "Module name"},
                                       {"defaultValue", "demo"}}};
tool.scaffolder = [](xsmp::ScaffoldContext& context) {
  context.writeFile(context.projectDir / "module.txt",
                    context.getPromptValue("moduleName").string());
  context.addDependency("Foundation");
};
```

A failing scaffolder rolls back the project it was creating.

## Include Built-in Model Files

The manifest `builtins` list adds reusable XSMP model files. They are visible only
to projects that enable the contribution, and they are not inherited through
project dependencies.

## Load and Test

VS Code discovers the manifests of all the installed extensions at startup, and
names their handlers to the server as it starts. So an extension installed later
needs a reload of the window. The command line takes `--extension <package-directory>`,
which can be repeated.

In the editor, a contribution that cannot load is reported with its descriptor, its
handler and the phase that failed, and the others still load. On the command line,
where you name each extension, it is an error.
